# GoreeCloud Search security and authority boundaries

**Development. No operational security or Production acceptance granted.**

1. The supplied wrapper `scripts/run-private.sh` requires a 32+-character secret and refuses public-interface, public-instance, GET, and unproxied-image overrides. It selects the loopback-only configuration.
2. JSON in the local profile is **not authenticated**. Never expose this profile to untrusted networks. A public GoreeCloud API needs separately verified Identity, Privacy Shield authority and API limits.
3. The private profile allowlists **24 category adapters in seven provider families**: Brave Search, Startpage, Qwant, DuckDuckGo, Ecosia, Bing and Google, with only approved Web, Images, Videos and News variants. Ecosia is Web-only, and Startpage does not support Videos. Other inherited engines remain excluded. Search and preview validate explicit names before dispatch. Provider inclusion does not prove independent indexing, anonymity or upstream request success.
4. Before public deployment, independently validate SSRF/XSS protections, rate limiting/Valkey, HTTPS and reverse proxies, secret management, query redaction, logging/retention, uptime, rollbacks and live security/privacy gates.
5. GoreeCloud UI (GC UI) is the current presentation authority. Search still carries a retired Glaze styling dependency pending controlled migration; neither UI layer implies consent, permission, authorized indexing, Identity state, Wardveil rules, or Production approval.
6. The private mode rejects external bangs and first-result navigation before provider dispatch; unexpected redirects are denied after a search. Explicit user clicks on result links can still disclose information to destinations.
7. Raw query length is checked before parsing operators. The submitted search remains POST-only, with selection caps before network dispatch. Private mode returns uncached 404 responses for direct `/opensearch.xml` and `/autocompleter` GET endpoints, blocking alternate browser-discovery and suggestion routes even if a client bypasses the interface.
8. Private mode rejects serialized GET and nonempty POST preference imports before decoding; upstream normally auto-applies shared settings links, which can silently change which providers a user searches. Ordinary local Preferences forms remain available and uncached. Private navigation never copies shared preference tokens into links.
9. Main clickable search results use a bounded HTTP(S) URL-scheme and authority guard in private HTML and JSON. This does not constitute complete safety validation of result template secondary links, embedded media, image proxies, outbound HTTP requests or the sites users choose to visit.
10. The represented-source display counts selected engine names carried on accepted primary result objects for this page only. It does not authenticate the provider, establish that an HTTP request succeeded, measure request volume, or cover discarded unsafe results, answers or infoboxes. This is a transparent result-label inventory, not a provider audit.
11. Private `POST /preview` is a no-network query-selection inspection. It parses the real search input with the same raw-size, fanout and redirect guards and creates no SearXNG provider executor. Its JSON mode with `format=json` deliberately omits raw query text; the HTML view retains the submitted query only in the protected POST-continuation form. Continuing or selecting a single source requires a separate explicit POST that may send the terms to configured third-party providers. This is not an independent provider health or privacy guarantee. Unsupported GET requests to `/preview` receive uncached 405, and the route is disabled outside the private profile.
12. Startpage remains subject to upstream proof-of-work / CAPTCHA blocking. GoreeCloud selects it as part of the approved **seven-provider** lineup; startup registration does not prove that any provider, including Qwant, is reachable. Never silently substitute a different provider on failure.
13. The private parser treats explicit `engines=` choices as an exact validated subset to prevent SearXNG's category+engine union from widening query disclosure. Bang/engine conflicts fail closed. Web, Images, Videos and News tabs submit via POST and select only per-category approved variants (at most seven families; Videos supports Brave, Qwant, DuckDuckGo, Bing and Google). A Startpage-only preference disables Videos rather than silently substituting another source. Browser-local preferences and pagination/header resubmission preserve validated selection.
14. Inherited upstream CI/release automation remains disabled. Bounded source/runtime and synthetic browser tests are neither Production nor GC UI consumer acceptance.
15. Provider diagnostics for **Brave Search, Startpage, Qwant, DuckDuckGo, Ecosia, Bing and Google** must not expose request URLs, query-bearing POST data, cookies, or provider tokens. Redaction of all outbound paths and production telemetry still requires security qualification.
16. The opt-in `scripts/provider_health_probe.py` uses fixed synthetic terms against an already-running loopback-only Development service; it disables environment proxies and rejects redirects. A local probe does not prove upstream provider privacy or public deployment readiness.
17. The inherited `manage webapp.run` launcher originally hardcoded `GRANIAN_HOST=::` and `SEARXNG_DEBUG=1`, overriding the private script's loopback requirement. The development wrapper now disables debug/hot reload and `manage` respects `SEARXNG_BIND_ADDRESS` when supplied. Launcher contract tests guard against this regression. Static checks and browser CI do not replace an actual socket-binding audit before provider traffic or deployment.

18. Startpage explicit blocking at https://cdn.startpage.com/sp/cdn/error-pages/blocked.html is classified as provider access denied rather than a successful empty response. This does not bypass its block or authorize an alternate engine. Synthetic offline adapter tests cover known and spoofed locations.
19. A real pinned Granian 2.8.4 listener is tested on an ephemeral 127.0.0.1-only socket with no provider traffic and a clean process-group shutdown; GitHub Actions runs the same check independently. This verifies the listener interface for the tested profile, not reverse-proxy, public network, or full managed-wrapper deployment acceptance.
20. Seven-family Development source now configures `outgoing.using_tor_proxy: true` with local `socks5h://127.0.0.1:9050`. Private provider transport refuses missing Tor verification and re-attests each reused or newly created client, closing the client on a failed response instead of accepting a cached success. Per-engine configuration may not disable the mandatory Tor setting. The real `curl_cffi` SOCKS5H regression connects only to a deliberately rejecting loopback relay, confirms that the attempted remote-DNS hostname is the Tor Project attestation endpoint rather than a search provider, and verifies that no provider request succeeds after denial or relay loss. These source and synthetic tests do not prove the VPS firewall blocks direct egress, that image-proxy and every other outgoing path is isolated, or that DNS rebinding, IPv6, user-IP masking, Tor circuit behavior, real provider access, public Identity/rate limiting, rollback and Stable acceptance are satisfied. The opted-in approved-document native index is not a general web engine and must not be silently included in All Sources.
21. Disposable GitHub-hosted Docker staging uses two internal-only synthetic bridges to verify direct visitor/provider separation, refusal of public IPv4/IPv6 and metadata destinations, blocked external DNS, and fail-closed gateway outage followed by synthetic reconnection. This is not an actual Tor-network or Search-image rollback proof. Read-only VPS inspection still shows the running Tor/Search namespace joined to the non-internal `proxy` bridge. A single explicitly proxied live attestation returned `IsTor=True`, which is limited to that request and must not be described as an application-wide leak qualification.
22. The opt-in native document crawler's `PinnedHttpsFetcher` separately enforces an explicit HTTPS hostname allowlist and canonical URL before DNS resolution, rejects any non-global address in a DNS answer, and pins the checked IP for its TLS connection while retaining the original hostname for certificate verification. Offline adversarial tests cover disallowed direct fetch calls, mixed public/private DNS answers, IP pinning, and oversized responses. This is defense in depth for the source fetch boundary; it does **not** prove that live container/VPS egress is isolated, DNS and routing controls hold under all network conditions, the endpoint has permission to index a site, or any Production security gate has passed.
23. A separate Development source candidate extends the common provider-target guard to GoreeCloud's `private_search: true` direct-HTTPS **free-first** profile, even though `require_anonymous_egress: false` deliberately disables the Tor requirement. For every initialized Search network, this guard rejects malformed, local, metadata, non-HTTPS, credential-bearing and nonstandard-port destinations before opening a client; suppresses automatic response redirects, including explicit request overrides; denies per-request proxy/interface and insecure transport overrides; and strips identifying request headers/cookies. The earlier Tor-only privacy-proxy enforcement remains intact. Synthetic offline tests cover 301/302/307/308 and adverse inputs, and a fresh interpreter checks real free-profile network initialization. This candidate **is not deployed**. Static URL validation does not prevent DNS rebinding after resolution, so isolated target-runtime egress/firewall/DNS/IPv6 denial and real provider compatibility must be verified before changing the live Development image or resolving the remaining security issue.
